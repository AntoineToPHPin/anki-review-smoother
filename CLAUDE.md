# Review Smoother — context for agents

Anki add-on ("Review Smoother" on AnkiWeb; repo `anki-review-smoother`) that reshapes each deck's upcoming review forecast into a smooth descending curve — e.g. 4/day, then 3/day, then 2/day — instead of a jagged 5, 2, 4, 3… It only moves due dates; it never changes how many cards there are.

The author discusses in French; everything in the repo (code, comments, README, UI strings) is English because the add-on is meant for wide sharing. The UI is translated to French (see `i18n.py`).

> **Keep this file up to date** without being asked: remove open items once resolved, add durable conventions, design decisions and gotchas. Only what someone resuming cold needs — not task-by-task progress.

## Design decisions (agreed with the author)

- **Target curve**: computed automatically per deck, nothing to enter. A manual per-deck curve (e.g. `4x14, 3x28, 2x48`) was planned, then **dropped by the author on 2026-11-11**: the automatic curve suits them. Don't reintroduce it unless asked (if it ever is: a fixed curve rarely matches the day's card count, so it needs a policy such as "cap per day, filled from day 1" vs "proportional rescale").
- **Moves**: cards are almost always *advanced*. Postponing is the exception (decided 2026-11-11): margin **10% of the interval**, **longest intervals first**, budget **1% of the window's cards (at least 1)**, used **only to lower the peak at the start of the curve**. **Off by default since 2026-11-12** (author's choice, `allow_postpone` config, was on before), with a dialog checkbox that recomputes the preview instantly. On `Paroles de chansons` it postpones 1 card from day 1 to day 2 for a peak of 54 instead of 55: the author keeps that behaviour (no minimum-gain threshold) but wants the option unchecked.
- **Horizon**: 90 days by default, configurable. Day 1 = tomorrow; today, overdue, new, learning, suspended and buried cards are never touched.
- **Window edge** (decided 2026-11-12): cards due in the **next quarter of the horizon** after it (`LOOKAHEAD = 0.25`, `lookahead_end(horizon)`: 90 → up to day 112, 30 → day 37) may be **pulled into the window** (advanced), so the end of the window does not drop just because the cards due right after it are left out (`Histoire`: days 89–90 were empty with cards due on days 93 and 96). Cards due later than that are never touched, and cards that stay after the window keep their due day. The author chose the quarter after comparing with "as long as the horizon" (pulls more, from further away — e.g. lengthens Bépo's plateau of 2s) and "10% of the horizon" (only the very edge). Accepted consequence: on sparse decks the block of 1s extends into the trailing 0s (PHP: 4 cards pulled). On Bépo that made a `1x32` tail, which led to evening out down to 0 (see `even_out`).
- **Trigger**: manual only — a menu action opening a dialog with a before/after preview, confirmation, and undo.
- **Preview graph**: must look like Anki's Statistics "Future Due" graph (French UI: « Charge de travail », ftl key `statistics-future-due-title`). Reimplement it — do not copy Anki's code (AGPL; this repo is MIT).
- Only the due date changes; the interval is kept.

## Layout

- `review_smoother/` — the add-on folder itself (what gets installed in `addons21/`).
  - `smoothing.py` — pure logic. **Must not import `anki`/`aqt`**, so tests and tools can import it outside Anki.
  - `__init__.py` — Anki entry point. Only imports `ui` when `aqt.mw` exists, so the package (and `smoothing`) stays importable outside Anki for tests and tools.
  - `web/graph.js` + `web/graph.css` — before/after graphs (inline SVG, no library), shown in an `AnkiWebView` in the dialog: files are read and inlined into `stdHtml()`, then `render({before, after})` is called via `web.eval()` (queued by Anki until the page is ready). Look copied from Anki's Future Due graph by inspecting its bundle (`_aqt/data/web/sveltekit/.../nodes/7.*.mjs` + assets CSS): ColorBrewer Greens from 0.7 (tomorrow) to 0.3 (horizon), translucent running-total area with a right axis (`--area-*` variables, light/night), tick text opacity .5 / 10px, grid opacity .1, gray hover columns. The tooltip is `position: fixed` and kept inside the viewport (flipped above/left of the cursor when needed): positioned in the page, it extended it near the bottom and made a scrollbar appear on hover. The dialog has a maximize button (`WindowMaximizeButtonHint`), so the graphs are **drawn at their real pixel size**: graph.css makes the two graphs share the page height (flex column, `html/body` at 100%), `render()` creates both sections first then each graph reads its svg's `clientWidth/clientHeight` for the viewBox (min 300 × 120), and redraws on `resize` (one per animation frame). Text keeps its size instead of being scaled with the window. **Horizontal zoom** (asked 2026-11-12, days only — the y scales never change): `view = {start, end}` shared by both graphs; mouse wheel zooms around the day under the cursor (×1.25 per notch, at least 7 days), dragging pans when zoomed (`#charts.zoomed` → grab cursor), double click shows all days. Plot contents are cut with a `clipPath` per graph (`clip-before` / `clip-after`); only visible days get bars and hover columns; day ticks come from `dayTicks(start, end)`. `render()` (new data from Python) keeps the zoom unless the horizon changed; `draw()` redraws, throttled to one per frame via `requestDraw()`. Zoom and drag were checked in headless Edge by dispatching `WheelEvent`/`MouseEvent` and reading a log with `--dump-dom`. Differences on purpose: one bar per day (Anki bins 2 days in its 3-month view) and a shared y scale for both graphs. Quick visual check outside Anki: build a page with the two files + `render(...)` and screenshot it with headless Edge (`msedge --headless --screenshot`).
  - `i18n.py` — every user-facing string, English + French, in `STRINGS` (no Anki import). `Translator(anki.lang.current_lang)` picks the language from Anki's interface (`fr_FR` → French, unknown → English); keys `x_one`/`x_other` are plurals chosen by `count` (French: 0 and 1 are singular). French follows Anki's own French wording (« Total cumulé », « Demain », « Dans 3 jours », « Paquet ») and typography (decimal comma, non-breaking space before `:` and `%`, typographic apostrophe). **Any new string goes into both languages**: `tests/test_i18n.py` fails if keys or placeholders differ. The graph gets its labels from `Translator.graph_strings()` inside the `render()` data. Qt's standard buttons (Apply/Cancel — Cancel rather than Close since 2026-11-12, at the author's request) are translated by Qt itself. `config.md` stays English.
  - `ui.py` — Tools menu entry + dialog: deck, horizon, before/after graphs, summary, Apply. The horizon has radio shortcuts « 1 mois / 3 mois / 1 an » = **30 / 90 / 365 days** (Anki's Future Due graph uses 31 / 90 / 365, checked in its bundle; the author chose 30 for a month), before the spin box, which still takes any value (7–365): a shortcut sets the spin box, the spin box checks the matching shortcut or none (`sync_range`, toggling `setExclusive` to uncheck). Labels are our own i18n strings: Anki has no reusable ftl key for them. `make_plan()` loads cards up to `lookahead_end(horizon)`; "before" counts window cards only; the summary's total is `Plan.total` (= cards in the window after smoothing, pulled ones included). `done()` calls `web.cleanup()`. Size (asked 2026-11-12, the minimum size was too small): first opening at 80 % of the main window's screen (`DEFAULT_SCREEN_SHARE`), then Anki remembers size, position and maximized state per profile via `restoreGeom(self, "reviewSmoother", default_size=...)` / `saveGeom` in `done()` (checked in bytecode: `default_size` is only used, through `resize()`, when nothing is saved). Under the graphs, a greyed `QLabel` hint on zooming (`zoom_hint`). A "Show cards to move" button (`ActionRole` in the button box, enabled when cards move) opens Anki's Browser with `aqt.dialogs.open("Browser", mw, search=("cid:…",))` (signature checked in Anki 26.09's bytecode: `Browser.__init__/reopen(mw, card, search)`); the dialog is therefore `WindowModal` (blocks the main window only), not application-modal, so the Browser stays usable. `make_plan()` (read-only) / `apply_plan()` (sets `card.due`, wrapped in `add_custom_undo_entry` + `merge_undo_entries` so it is one undo step, run via `CollectionOp`).
  - `stats_link.py` — "Review Smoother" **button** (the author preferred a button to a link; a plain `<button>` gets Anki's look from the page's global CSS, `button:not(.btn,.btn-close)`, only its size is set inline) next to the Future Due title (« Charge de travail ») in the Statistics window (`aqt.stats.NewDeckStats`, a sveltekit page; each graph title is an `<h1>`). `gui_hooks.stats_dialog_will_show` connects the webview's `loadFinished` to `eval` a script that finds the `<h1>` whose own text equals `col.tr.statistics_future_due_title()` and appends the link, again via a `MutationObserver` since the page builds and redraws its graphs after loading. A click sends `pycmd("review_smoother:open")`, caught by `gui_hooks.webview_did_receive_js_message` (context = the stats window): the dialog opens (via `QTimer.singleShot(0, …)`, not inside the bridge call) on the deck selected in the Statistics window (`deck_chooser.selected_deck_name`), and the stats are `refresh()`ed once applied. Hooks and names checked in Anki 26.09's bytecode; the script was checked on a fake page in headless Edge, not inside Anki.
  - `config.json` / `config.md` — `horizon_days` (default 90), `allow_postpone` (default false).
- `tests/` — `unittest` only (stdlib, no dependency): `python -m unittest` from the repo root.
- `tools/simulate.py` — **read-only** simulation on the real collection through AnkiConnect (`localhost:8765`, Anki must be running): `python tools/simulate.py "Deck::Name" [--horizon 90] [--postpone]` (postponing off by default, like the dialog). On Windows, prefix with `PYTHONIOENCODING=utf-8` for accented deck names in the output.

## Algorithm (`smoothing.py`)

- `auto_curve(counts)`: upper concave hull of the cumulative due counts = the lowest non-increasing *fractional* daily rate that never falls behind what is due (so advancing alone is always enough). Rounded **down** to whole cards on the cumulative curve — still ≥ the integer due counts, and moves cards less than rounding up. The alternating rounding (4, 3, 4, 3… / 1, 0, 1, 1, 0…) is then sorted descending into a staircase; sorting only moves cards earlier, so the constraint holds. **Sparse decks (< 1 card/day) end as a block of 1s followed by 0s — the author's explicit choice** (2026-11-10), rather than spacing 1 card every n days or a density that keeps decreasing below 1/day. Downside: on such decks some cards are advanced a large share of their interval (up to ~50% seen on `Informatique::PHP`). Accepted as is: the user picks which decks to smooth, and would not smooth a deck that sparse — so no max-advance limit for now.
- `smooth(cards, horizon, allow_postpone)`: entry point used by the UI and `simulate.py`. `cards` = cards due on days 1..`lookahead_end(horizon)`; returns the curve over the window only (its sum includes the pulled cards) and a new due for every card. The curve is computed over the extended period and only its first `horizon` days are used: `even_out` runs on the window part, `assign` on the whole extended curve, then cards assigned after the window are reset to their original due. Postponing only uses window cards (still capped at the horizon, so they never leave the window), budget = 1% of window cards, and the step/plateau rules look at `[:horizon]` only. A pile right after the window can hold the peak up, so the postpone loop also stops when lowering does not lower `target[0]` (without that check it looped forever). Starts from `auto_curve`; if allowed, tries to lower the first value (the peak) one card/day at a time via `_postpone_to_cap` (forward sweep: whenever cards due on days 1..k exceed cap·k, push one card a day later — preferably one already pushed, to postpone few distinct cards; else longest interval; tie → due latest, to push it the fewest days), keeping each lowering only while the postponed count stays within budget **and the lowered curve has no steeper day-to-day step than the advance-only curve** (added 2026-11-11 after the author found `Bépo::Caractères` much better without postponing: capping its steady slope 18, 17, 17, 16, 15… gave a 16 × 7-day plateau then a cliff to 13), **and the top plateau of `even_out(lowered)` is at most 1 day longer than the next plateau** (`_top_plateau_too_long`, added 2026-11-12: the deck had changed to `18, 17, 16×3, 14…`, whose 2-card step let the step rule accept `16×6, 15, 14…`; `even_out` never touches the top plateau. Not checked when the top or next plateau is the last day's level — e.g. `3×20`). Postponing is for isolated bumps, not for flattening steady slopes. Then `assign` on the shifted due days.
  - **Rejected first attempt** (don't retry): the lowest curve reachable with every card allowed its full 10% margin. It reshapes the whole curve and postponed 67/160 and 296/420 cards on real decks — not an exception. With the final rules (data of 2026-11-12): 1 card on `Paroles de chansons (entières)` (removes an isolated 4), 1 on `Bépo::Caractères` (18 → 17), none on `Paroles de chansons` or `Pays`.
- `even_out(curve)`: last step of `smooth()`, always applied. Goal: **going down the staircase, plateau lengths (days per level) grow gradually**. A block of plateaus at consecutive levels gives one day to the level above and one to the level below (first day +1, last day −1: one card moved earlier, never needs postponing; inner plateaus unchanged) when its top plateau is ≥ 2 days longer than the one above (a jump) and its bottom plateau is longer than the one below (a dip; ≥ 2 for a single plateau, which loses 2 days; ≥ 0 against the days at 0, see below). Jumps are handled from the peak down, each with the shortest block that can absorb it. History: single plateau asked 2026-11-11 (`14, 13, 12, 12, 12, 11, 10` → `14, 13, 13, 12, 11, 11, 10`); general blocks asked 2026-11-12 on Bépo (`10x1 9x2 8x4` jump, `5x7 4x6 3x11` dip) → Bépo tail now `10x2 9x3 8x4 7x5 6x6 5x6 4x7 3x8 2x9 1x13 0x15`.
  - **Down to 0** (asked 2026-11-12): when the curve ends at 1 or 0 card/day, days at 0 are a level like the others and the 1s plateau gives them days while it is at least as long: they absorb the jumps no dip can. The author prefers more days at 3 and 2 and fewer at 1, **even if it leaves empty days at the end of the window** (`Paroles (entières)`: `3x20 2x28 1x40` → `3x26 2x26 1x26 0x10`).
  - **Cost, accepted**: cards are advanced much further (Bépo up to 94 days, 73% of the interval, 49 days on average for 19 cards; Paroles (entières) up to 82 days, 68%). A max-advance limit per card was proposed and **dropped by the author on 2026-11-12** — don't reintroduce unless asked.
  - **Rejected attempt** (don't retry): minimising the sum of squared differences of adjacent plateau lengths by local moves. It got stuck on Bépo's `9x2 8x4`, broke the 2026-11-11 example and lengthened peaks (`Paroles (entières)` `4x2` → `4x8`).
  - **Peak**: a block of several plateaus never gives days to the peak's plateau (repeated, `4x5 3x37 2x46 1x2` would become `4x22 3x23 2x23 1x22`). A single plateau still may, one day at a time.
  - Otherwise (curve ending at ≥ 2) the plateau at the last day's level is excluded, also as a neighbour: its length only reflects where the window ends (`Pays`'s `3x37 2x46` must stay).
  - **Rejected attempts** (don't retry): smoothing the daily rate with a moving average then re-hulling changes nothing (a moving average of a descending curve stays at or below it, and the hull snaps back to the due counts); rounding the smoothed cumulative *up* instead inflates the curve (`18, 18, 16, 16, 16` on Bépo, a 5 on Pays).
- `move_stats()`: count / mean / max days / max share of the interval, for advanced and for postponed cards. No wording here: sentences are built by `i18n.Translator.describe_moves()`.
- `assign(cards, target)`: fills days from the last one backwards, each day taking the available cards (due on or after it) with the **shortest interval** first. This minimises the total relative advance Σ (due − new_due) / interval — proven against brute force in the tests. Raises `InfeasibleCurve` if the target would need postponing. It may **chain moves** (e.g. a long-interval card J6 → J3 and a short-interval card J7 → J6 rather than J7 → J3 directly), so it touches more cards than strictly needed. **Kept on purpose (author, 2026-11-11)** after comparing with a "fewest cards moved" variant: about a third fewer cards moved, but each moved further relative to its interval (e.g. `Dates Histoire`: 19 → 11 cards, max advance 15% → 32% of the interval). Don't switch unless asked.
  - **Siblings** (asked 2026-11-12): `Card.note` (None = no sibling). A card is not *moved* to a day where a card of its note is due — before smoothing, already moved there, or in `taken` (note → days of sibling cards smoothing does not move: other decks, due later; `ui.sibling_days`, queues 2 and 3, not in filtered decks) — while another available card can take the slot; otherwise it goes there anyway rather than failing. Cards staying on their day are never moved for this, so siblings that were already due together stay together (25 cards on `Bépo::Caractères`; separating them would be a separate feature). Result on Bépo: smoothing used to create 2 same-day siblings, now 0; other decks created none. Not handled: postponed cards (postponing ignores siblings; it is off by default). `simulate.py` prints "cards sharing their day with a sibling" before/after.

## Local dev install

On the author's Windows machine, `%APPDATA%\Anki2\addons21\review_smoother` is a **junction** to this repo's `review_smoother/` folder: code changes apply after restarting Anki. Anki writes `meta.json` (user config overrides) into it — git-ignored. (`cmd /c mklink /J` fails from Git Bash; use PowerShell `New-Item -ItemType Junction`.)

## Environment gotchas

- Python 3.13 was installed with winget on 2026-11-12 (Anki's bundled Python has no `python.exe`). A shell started before that install may still resolve `python` to the Microsoft Store stub: reload `PATH` from the registry or restart VS Code.
- The author applies smoothings and reviews between sessions: real-deck figures (including the examples in this file) go stale quickly. **Re-run `simulate.py` before quoting a deck's curve**; the dialog is the reference.
- AnkiConnect requests must be sent as UTF-8 bytes; non-ASCII deck names fail otherwise.
- AnkiConnect has no "today" action: `simulate.py` deduces Anki's day number from a card found with `prop:due=N`.
- Target Python: Anki 26.09 bundles Python 3.13, but keep the code compatible with older Anki versions' Python 3.9 (`from __future__ import annotations`, no `match`, no `X | Y` at runtime).
